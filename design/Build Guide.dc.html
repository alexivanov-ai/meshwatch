Meshwatch — build guide Windows first, macOS second
Written for someone who can copy and paste commands

Building Meshwatch with Claude Code

This turns the prototype into a real installable desktop app that scans your network, talks to your TP-Link gear, reads Pi-hole, and audits firmware. You will not write code — you will paste prompts into Claude Code and paste commands into a terminal. Budget a weekend for a working v1, and expect the TP-Link parts to be the fiddly bit.

1 · What you end up with

An Electron app. Electron is the same technology behind Slack and VS Code: a desktop window wrapped around a web page, with full access to your network from the Node.js layer underneath. It matters here for three reasons — the prototype's interface transfers almost directly, the network-scanning libraries you need already exist in JavaScript, and one config file produces both a Windows .exe installer and a macOS .dmg.

The alternative, Tauri, produces much smaller apps but needs Rust. For a first build with Claude Code doing the work, Electron is the safer road.

One honest limit up front

You can build the Windows installer on Windows. You cannot build a macOS .dmg on a Windows machine — Apple's tooling only runs on macOS. You have a MacBook Pro, so run the same project there when you want the .dmg. The code is identical; only the build command differs.

2 · Install four things

On the Windows machine, in this order:

What Where Why
Node.js LTS nodejs.org — the left-hand "LTS" button Runs the app and the build tools
Git git-scm.com Version history, so a bad change is undoable
VS Code code.visualstudio.com Where you will run Claude Code and see the files
Npcap npcap.com — tick "WinPcap API-compatible mode" Lets Windows do raw ARP scanning. Without it, discovery finds far less

Then install Claude Code. Open VS Code, press Ctrl + ` to open its terminal, and paste:

npm install -g @anthropic-ai/claude-code

Make the project folder and start Claude Code inside it:

mkdir %USERPROFILE%\meshwatch
cd %USERPROFILE%\meshwatch
git init
claude

It will ask you to sign in the first time. From here on, everything in sections 3 to 7 is text you paste at the > prompt, one section at a time. Do not paste them all at once. Let each phase finish and check it works before moving on.

3 · The opening prompt

This sets up the project skeleton and tells Claude Code the shape of the whole thing. Paste it whole:

Build me an Electron desktop app called Meshwatch. I am not a developer — explain nothing unless I ask, but tell me clearly whenever I need to run a command or make a decision.

It is a local network monitoring dashboard for my home network, 192.168.0.0/24. The gateway is a TP-Link Archer BE220 at 192.168.0.1. A Raspberry Pi 5 at 192.168.0.2 runs Pi-hole and is the DHCP and DNS server for the whole network; I reach it over SSH on port 2222.

Set up the project now: Electron with a main process and a renderer, electron-builder configured for a Windows NSIS installer and a macOS dmg, and secure IPC (contextIsolation on, a preload script exposing a narrow API — never enable nodeIntegration in the renderer). Use plain HTML, CSS and JavaScript in the renderer, no framework and no build step for the UI. Store data in a local SQLite file via better-sqlite3 so device history survives restarts.

Create a CLAUDE.md recording those facts about my network so you remember them in future sessions. Then show me how to run the app in development, and stop — I want to see an empty window open before we go further.

When it finishes, it will tell you to run something like npm start. An empty window should appear. That empty window is the milestone — if it opens, the hard scaffolding is done.

4 · Discovery — the engine

This is the part that actually finds your devices, and it is worth doing before any interface. Four discovery methods overlap; together they identify far more than any one alone.

Now build the discovery engine in the main process. It should run four scans and merge the results into one device list keyed by MAC address:

1. ARP sweep across 192.168.0.1–254 to get every IP and MAC that answers. 2. mDNS/Bonjour browse to pick up Apple devices, the Sony TV and the printer-style services. 3. SSDP/UPnP discovery — this is how the GREE air conditioner and the PlayStation announce themselves. 4. DHCP lease list read from the Pi-hole over SSH, which gives real hostnames the other three methods miss.

Resolve each MAC's manufacturer from the IEEE OUI prefix list — bundle the list locally, do not call a web service. Treat the DHCP hostname as the best name, the mDNS name as second best, then the OUI vendor, then "Unidentified host".

Infer the topology as a tree: the BE220 is the root; the Raspberry Pi, the unmanaged 8-port switch, the RE450 extender, the TL-WA1201 extender, an Archer AX20 in AP mode, an old TL-WDR4300 and a Broadcom access point sit under it; clients hang off whichever node they associated with. Get parentage from each TP-Link node's client table where you can, and from RSSI plus lease origin where you cannot. Mark every inferred link clearly as an estimate — I would rather see "estimated" than a confident wrong answer.

Save every scan to SQLite with a timestamp so I can see when a device first appeared and when it was last seen. Then write me a command-line test I can run to print the discovered device list, so I can check it against what I know is on my network.

Run its test. Compare the output against your real kit. If devices are missing, say so plainly — "the GREE air conditioner and the Broadcom AP did not appear, find out why" — and let it investigate. This is the phase to be stubborn about; everything else is built on it.

Run it as administrator

Raw ARP scanning needs elevated privileges on Windows. If the scan returns almost nothing, close VS Code, right-click it, choose "Run as administrator" and try again. Ask Claude Code to make the finished app request elevation on launch.

5 · The Pi-hole and the SSH console

The Pi is the most rewarding piece to wire up, because it is the one device with a real API and a real shell — and because it holds the DHCP truth that names everything else.

Now add Pi-hole integration for the Raspberry Pi 5 at 192.168.0.2. Use two channels: Pi-hole's REST API for statistics (query totals, percentage blocked, top blocked domains, the DHCP lease table), and SSH on port 2222 via the ssh2 library for shell commands.

Authenticate SSH with a key, not a password. Walk me through generating the key on this machine and installing it on the Pi, one command at a time, and check it works before continuing. Store the key path and the Pi-hole API token in the OS credential store — Windows Credential Manager, macOS Keychain — never in a config file in the project.

Give me a panel with a terminal-style output area and buttons for the commands I actually use: pihole status, pihole -g to rebuild gravity, restart pihole-FTL, list DHCP leases, show top clients, check CPU temperature and disk space, and check for apt updates. Any command that interrupts DNS for the whole house — restarting FTL, rebooting the Pi — must ask me to confirm first and warn me how long name resolution will be down.

Also let me type an arbitrary command into the panel and see its output.

6 · TP-Link control

Read this section before you paste it. TP-Link publishes no official local API for consumer routers like the BE220. Community libraries reverse-engineer the encrypted local endpoint the Tether app uses, and firmware updates sometimes break them. Expect this phase to be the least reliable, and expect to fall back to opening the router's own web page for some actions.

Now add TP-Link device control. My devices: Archer BE220 (gateway, 192.168.0.1), Archer AX20 in AP mode, RE450 extender, TL-WA1201 extender, and an old TL-WDR4300 that is end-of-life.

First, research and tell me honestly which of these can be controlled locally and which cannot, before writing any code. There is no official local API, so tell me which community library you propose, how actively maintained it is, and what breaks if TP-Link changes firmware. I would rather have five working actions and honest gaps than nine that fail silently.

Then implement what is genuinely possible, aiming for: reboot, firmware version check and update, SSID and password per band, band steering and channel selection, the per-node client list, port forwarding rules, a WAN speed test, LED on/off with a schedule, and mesh backhaul signal health.

Store router credentials in the OS credential store. Every action that interrupts connectivity must ask for confirmation. Where an action cannot be done through the API, give me a button that opens that device's own admin page in my browser instead of a button that pretends to work.

Treat the TL-WDR4300 as legacy: read-only, flagged as end-of-support, no control attempted.

7 · The security audit

Now add the security audit. For every discovered device, check what can be checked and be explicit about what cannot:

Compare the running firmware against the latest release where a vendor feed exists. Flag devices past end of support — my TL-WDR4300 is one. Scan common service ports on each host and flag risky ones: telnet 23, raw print 9100, unauthenticated UPnP, and the GREE air conditioner's UDP 7000 local API. Flag any device whose MAC matches no vendor and that has no DHCP hostname. Check the router for WPS enabled, UPnP enabled, remote management exposed to the WAN, and admin interfaces served over plain HTTP.

For the four devices with no management API — the unmanaged switch, the Broadcom AP, the GREE unit, and anything unidentified — infer what you can from ARP timing, lease history and how long they have been seen, and label every inferred value clearly as an estimate. Let me hand-record a firmware version I have read off the device myself, so age warnings still work for them.

Give each finding a severity, a plain-English explanation of the actual risk, and one concrete action. Compute an overall score. Cite the CVE where a real one applies and say "unverifiable" where none can be established — never invent one.

Add per-device internet blocking, applied through Pi-hole for DNS-level blocking and through the router where a MAC filter is available.

8 · Making it look like the prototype

Export the prototype from this project as a standalone HTML file and drop it into the project folder. Then:

I have put a design prototype at prototype.html in this folder. Read it and rebuild the app's interface to match it exactly — the same layout, spacing, type, colours and interaction structure: sidebar navigation, overview with statistics and a needs-attention list, inventory table with filters, topology tree, security audit, the Pi-hole and SSH view, discovery progress with a live log, and preferences. Wire every part to the real data from the engine you already built. The prototype's data is invented; replace all of it, keep the design.

9 · Building the installers

On Windows, this produces an installer in a dist folder:

npm run build:win

Copy the whole project folder to your MacBook Pro, run npm install there, then:

npm run build:mac

Both installers will warn on first launch that the app is from an unidentified developer, because it is unsigned. On Windows, click "More info" then "Run anyway". On macOS, right-click the app and choose "Open". Signing certificates cost money annually and are only worth it if you distribute the app to other people; for your own machines, ignore the warning.

10 · What will go wrong

Symptom Cause and fix
Scan finds three devices Not running as administrator, or Npcap missing. Both, usually.
Phones appear and vanish Correct behaviour. Private MAC randomisation and Wi-Fi sleep. Ask for a grace period before marking a device offline.
Router control fails after a firmware update The community library broke. Expected. Fall back to the web admin page and ask Claude Code to update the library.
The whole house loses internet mid-build You restarted Pi-hole FTL or rebooted the Pi. It comes back. This is why those actions need confirmation dialogs.
Port scanning trips your own security software Your antivirus is doing its job. Whitelist the app. Only ever scan your own network.
better-sqlite3 won't install Native module needs build tools. Ask Claude Code to fix it — it knows the incantation.

11 · Habits worth keeping

Commit after every phase that works — type "commit this with a clear message" and Claude Code handles it. That gives you a point to return to when something breaks. Keep CLAUDE.md up to date with anything about your network you find yourself re-explaining; it is read at the start of every session. And when something does not work, describe the symptom rather than guessing the cause — "the GREE unit shows as unidentified even though I know its IP is 192.168.0.32" gets you further than a theory about ARP.

Finally: build the phases in the order above. The temptation is to make it pretty first. Discovery is the app — if it finds your devices reliably, everything else is decoration you already have designed.
